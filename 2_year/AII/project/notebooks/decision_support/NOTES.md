## The three parallel tracks

Decision support is not one model with three parts bolted on. It is three tracks that read the same risk score and produce three independent judgments about it, and they can be built and evaluated in parallel by the same person or split further if time is tight.

Track one, the cost model, answers what should be done. Given a risk score, it chooses a next check in interval that minimizes expected cost under an explicit, documented cost model, following Predict then Optimize as covered in 08-dfl-tf, lesson 1, PFL and DFL. The parallel technique worth trying here, once the basic version works, is Decision Focused Learning, training the upstream risk model directly against the cost rather than against a proxy loss like cross entropy, which 08-dfl-tf, lesson 2, Applicability of DFL frames as most useful exactly when the decision has a recourse like structure, missing one check does not mean the patient is lost since a later check can still catch it, which describes a multiple choice monitoring interval well.

Track two, the fairness audit, answers whether that recommendation treats people differently across PTGENDER, PTEDUCAT, and PTMARRY, using the Disparate Impact Discrimination Index from 07-ciml, lesson 1, Fairness in ML Models. This runs on the same recommendation the cost model produces, not as a separate model, and is what gives point three a second, genuinely distinct axis of evaluation beyond raw cost.

Track three, attribution, answers why the score is what it is for one specific patient, using SHAP values from 06-at, lesson 4, Additive Feature Attribution, on top of a Logistic Regression or Lasso baseline as covered in 06-at, lesson 2, A Baseline Approach. Boruta all relevant feature selection from lesson 5 runs once, offline, to sanity check which biomarkers the model leans on against which ones the anomaly detection and RUL stages already flagged as informative.

All three tracks read the same risk column. None of them depends on the other two finishing first, which is what makes them genuinely parallel rather than three sequential steps with a shared name.

## The subject level split

Every track below is evaluated on a train and a test split, split by RID rather than by row, following util.partition_by_machine from 04-rul, which splits by machine before ever touching a row since its own running example has many rows per machine, the same shape final.csv has, many rows per RID, a median of 3 visits per patient and as many as 20. subject_train_test_split in decision_util.py does this with sklearn's GroupShuffleSplit, and the notebook checks explicitly that no RID appears in both splits before moving on.

This matters for every track differently. The cost model policy needs no fitting, so the split mainly checks that the fixed versus adaptive comparison holds up outside the exact rows it was first looked at on, not only on them. The DIDI figure is computed on both splits mainly to confirm it is not an artifact of one particular sample of patients, since DIDI itself audits a cohort of predictions rather than a fitted model. The attribution track is where the split actually matters most, since a model can always fit its own training rows better, and only the test split answers whether a more flexible model is really capturing something real or only fitting noise more closely.

## The cost model, in more detail

A recommended check in interval only means something against an explicit cost. The two costs that matter here are a routine monitoring cost, the cost of one clinical check, and a missed conversion cost, the cost of a patient converting between two scheduled checks without being caught in time. These numbers cannot be estimated from ADNI and have to be stated as assumptions, then the recommendation tested under more than one setting of them, exactly the caveat the implementation plan already raises in its open questions section.

The direct course analogue is RULCostModel from 04-rul, instantiated as util.RULCostModel(maintenance_cost, safe_interval) and called as cmodel.cost(group_ids, predictions, threshold, return_margin=True), returning a total cost, a failure count, and a margin. ConversionCostModel below follows that exact calling convention, maintenance cost becomes a routine check cost, safe interval becomes a minimum clinically sensible check spacing, and the machine id array becomes the RID array, so a teammate who has read 04-rul can read this class without translation.

One detail worth flagging since it was easy to get wrong and only showed up once the notebook actually ran end to end. The missed conversion cost has to scale with the length of the interval being evaluated, not stay fixed once a risk threshold is crossed, since a conversion missed during a 3 month gap is a smaller failure than the same conversion missed during a 12 month gap. Both the function that chooses a policy and the function that scores a policy need to scale it the same way, otherwise a policy gets chosen under one cost model and scored under a different one, which can make an adaptive policy look worse than a fixed one even when it is making the better choice on every row. Both functions in decision_util.py take the same reference_interval_months parameter for exactly this reason, and the notebook defines the cost values once and passes them to both rather than repeating the numbers in two places.

## Correcting fairness at training time, not only measuring it after

Track two above treats DIDI as an audit, computed once a model already exists, on whatever it happened to learn. 07-ciml, lesson 2, Lagrangian Approaches for Constraint Injection, asks a different question, can the constraint be pushed into training itself, so the model is optimized against accuracy and fairness together rather than fairness being discovered afterward with no way to act on it short of retraining from scratch with different features. The lesson reframes the DIDI bound as a Lagrangian penalty added to the loss, argmin over theta of the expected loss plus lambda times max of zero and DIDI of the model output minus a chosen threshold, and studies two ways of setting lambda, a fixed value chosen by hand, and a dual variable trained by gradient ascent at the same time the network weights train by gradient descent, alternating between the two.

CstDIDIRegressor and LagDualDIDIRegressor in decision_util.py follow this pattern directly, each wrapping a small keras.Model subclass with a custom train_step, matching the lesson's own structure rather than reimplementing the constraint some other way. CstDIDIRegressor takes alpha as a fixed number, exactly the lesson's first version. LagDualDIDIRegressor instead carries lambda as a tf.Variable updated by its own optimizer inside train_step, a second gradient tape and a second apply_gradients call alongside the one for the network weights, so one call to fit trains both at once the way the lesson's dual version does. This runs in TensorFlow specifically, not the Lasso and Random Forest of track three, because the constraint has to sit inside a differentiable training loop with two coupled gradient computations, which is what the course material itself uses for this exact lesson.

This section only exists because three real bugs showed up while getting it running, each worth recording since two of them are not obvious from reading the lesson slides alone.

The first is narrow to this Keras version. A locally defined class named with a leading underscore, keras.Model subclasses defined inside init the way the lesson itself nests its model definition, gets rejected by Keras 3 with a root scope name error, not by any logic in the constraint, purely a naming rule. The fix is to give the inner class an ordinary name instead, KerasCstDIDIModel and KerasLagDualDIDIModel here, keeping the class itself defined locally inside init since that stays closest to how the lesson nests its own definition.

The second is specific to the dual variable. Setting trainable equal to False on the tf.Variable holding lambda, which reads at first like the safe choice since lambda should not be updated by the main optimizer, actually blocks gradient ascent on lambda too, since GradientTape will not track a variable marked non trainable at all. The variable has to stay trainable, and what keeps the main optimizer from also touching it is that Keras only ever updates model dot trainable variables, which covers layer weights, not an arbitrary tf dot Variable attribute sitting on the model, so removing the trainable equals False flag fixes the ascent step without letting the descent step drift into updating lambda by accident.

The third is the one worth remembering past this project. Fitting the same StandardScaler used for the Lasso baseline over the entire feature matrix, including PTGENDER and the bucketed PTEDUCAT column, silently breaks the constraint rather than raising an obvious error at first. The penalty term matches rows into protected groups by comparing a feature column against the literal category values passed in, one and two for PTGENDER, but standardizing those columns turns one and two into arbitrary floats, so the match selects zero rows for every group, an empty tensor's mean is not a number, and that not a number propagates through the whole loss from the very first epoch, not as a late divergence but as a wrong result from the first step. The fix, scale_excluding_protected in decision_util.py, standardizes only the columns that are not protected attributes and leaves PTGENDER and the education bucket in their original values, which is also the more defensible choice on its own terms, protected columns should stay legible during training precisely because the loss needs to read their real categories, not only at evaluation time.

One more finding sits alongside these three, not a bug exactly, a modeling choice that mattered more than expected. The lesson's simplest architecture is a single linear output neuron with no hidden layer, which underfits this dataset badly enough to give strongly negative R squared, checked directly by comparing hidden equals empty tuple against one hidden layer of eight units side by side on the same split, negative two point two against zero point five on the training rows. The eight unit hidden layer, the lesson's own second, more expressive architecture, is what every Lagrangian model below actually uses.

With those four issues resolved, the notebook trains an unconstrained baseline, a fixed lambda model with alpha set to five following the lesson's own guess, and the dual lambda model, all three on the same eight column feature set with the two protected columns held out of standardization, and reports R squared and DIDI for each on both splits. The unconstrained model's own training DIDI sets the threshold the constrained versions are held to, half of that value. On the training rows both constrained versions do bring DIDI down from the unconstrained figure, and the dual lambda version does so while landing a noticeably higher R squared than the fixed lambda version, which matches what the lesson claims for the dual approach over a hand chosen constant. On the test split the picture is more honest than clean, R squared for all three drops sharply, expected given this track's usable rows after dropping missing amyloid, tau, and phosphorylated tau readings are a few hundred, and DIDI on the test split does not track the training split's ordering at all, the fixed lambda version actually shows the highest test DIDI of the three despite having the lowest training DIDI. That reads as the small test sample not being large enough for a cohort level fairness statistic to generalize cleanly, DIDI audits a distribution rather than a single prediction, and a distribution over roughly two hundred rows split further into subgroups is a noisy thing to measure twice and expect to match. The accuracy side of the comparison, dual lambda beating fixed lambda, is the part of the lesson's claim that does replicate here, and is reported as such, the fairness side is reported as an open question this sample cannot settle rather than stretched into a conclusion it does not support.

## A fourth interval policy, reading the forecast directly

forecast_adaptive is the fourth interval policy, and the first to read point two's own forecast directly rather than a single risk number. hazard_survival_model.ipynb's chosen estimator produces a per visit hazard, forecast_conversion_probabilities in util/hazard_util.py turns that into a conversion probability at 3, 6, 12, and 24 months by compounding the persistence approximation across future steps, the same cumulative survival formula the implementation plan's point two section already names. recommend_interval_forecast in decision_util.py searches the same interval menu as the other three policies, fixed, snapshot adaptive, and trajectory adaptive, but prices each candidate against the forecast probability at that candidate's own horizon rather than one number rescaled by interval length, cost_from_forecast rather than cost, following the same Predict then Optimize structure as the others, 08 dfl tf, lesson 1, just fed a richer prediction.

This is not on the same cost scale as the other three, worth stating as plainly here as it is in comparison.ipynb and in temporal_window/4_forecast_adaptive.ipynb itself. On the test split, forecast_adaptive's own total cost is roughly twice snapshot_adaptive's and trajectory_adaptive's, 38795.6 against 18387.1 and 18710.4, while its catch rate is actually a little higher, 91.4 percent against 88.3 and 87.3. Checked directly, on the same rows with a real forecast, forecast_adaptive recommends the shortest, 3 month interval for 99.5 percent of test rows, where the identical rows under a snapshot only policy split much more evenly, 56.1 percent at 3 months and the rest spread across 6 and 12. That is the mechanism behind the higher cost, not a bug in how the cost gets computed, cost_from_forecast never rescales by interval length the way cost does, so it is pricing a genuinely different, structurally larger quantity once a probability compounds across several future steps.

The root cause traces back to the calibration point raised in the swap section above. hazard_survival_model.ipynb's own 0.791 AUC checks ranking, not calibration, and compounding an uncalibrated per visit probability across up to eight future steps amplifies whatever gap already exists there, consistent with a roughly constant 30 percent hazard every 3 months pushing the compounded probability high enough that recommend_interval_forecast finds the shortest interval cheapest almost everywhere it can reach. A sensitivity check across the documented cost multiplier range, 1.5, 2.8, and 4.0, does not change this picture, total cost moves with the multiplier as expected, 28001.6 up to 48662.3, but the near universal shortest interval recommendation holds throughout.

None of this makes forecast_adaptive wrong to have built, it prices real risk more honestly in principle, a genuine multi horizon forecast rather than one snapshot, and it is kept in every comparison on its own terms, reported separately rather than folded into a ranking it does not belong in. What it needs before its own total cost can be read as a real expected dollar figure is a calibration check on hazard_survival_model.ipynb's own estimator, predicted probability against observed frequency within bins, the natural next step this project has not yet taken.

## Fairness and explainability, a proposal for a joint design with the anomaly detection stage

Resolved, this joint design happened. `notebooks/pipeline/full_pipeline_reevaluated.ipynb` and `notebooks/decision_support/evaluative_synthesis.ipynb` both run the fairness and explainability pieces described below on a shared pipeline signal rather than on Point 3's output alone, checking `DIDI` at each stage a signal passes through, not only at the end.
>
> The `DIDI` and Lagrangian machinery in decision_util.py, `compute_didi`, `CstDIDIRegressor`, and `LagDualDIDIRegressor`, is already built, tested, and matches 07-ciml lessons one and two closely enough that the open question is not really which technique to use, it is which signal it should run on. Running it once on the final recommendation, once the full pipeline exists, is the easy version. The more useful version, and 07-ciml's own point that a disparity can hide inside an intermediate signal even when the final decision looks fair, argues for auditing `DIDI` at each stage a shared signal passes through, point one's own `ANOMALY_SCORE` or `HI`, point two's `HAZARD_ESTIMATE`, and point three's recommendation, rather than only at the end. That gives the anomaly detection stage a concrete way into fairness work on its own output too, not only a consumer of whatever Point 3 decides.
>
